---
title: Maintenance and recovery
description: Durable acceptance, archival retries and coordinated backups.
---

A cluster Durable Object commits accepted samples and deduplication state
transactionally before returning an OTLP success. Queue notifications start
archival work; durable alarms retry it if notification delivery fails.

Raw and summary objects are compressed, immutable and content checked. D1
indexes are published after successful upload. The archival outbox clears
only committed samples and retains concurrently arriving generations.
Storage failures preserve the buffer and can return retryable backpressure.

## Backup

Protect D1 configuration and archive indexes, Durable Object state, credential
verifiers and R2 objects as one logical system. An index backup without its
referenced objects cannot recover telemetry. Use provider recovery facilities
and protected exports according to your account's retention and plan limits.

Rehearse recovery into an isolated target. Verify object checksums, identity,
profile revisions, pending buffers, retry deduplication, history and source
freshness before redirecting agents or clients. Keep private backup receipts
outside public source and release artifacts.

## Migration and rollback

Preserve workspace/cluster identities, verifiers, revocation state, profiles,
source/start timestamps, exact raw values, original metadata, inventories and
lifecycle evidence. Use one authoritative writer during cutover.

Record the cutover boundary. Drain or replay pending data and independently
compare the candidate's current values and history. A rollback must reconcile
data accepted after the boundary before returning to an earlier database.
Changing DNS alone does not provide that recovery.

Migration endpoints are disabled in normal deployments. Enable
`MONITOR_MIGRATION=1` only for an isolated restore target. While enabled, machine
writes and normal operator mutations return retryable `503`; the target cannot
accept live agent traffic or collection-control changes. Expiration is suspended
on this isolated target so its imported base stays stable until source retention
deletions are reconciled. Normal deployment resumes expiration.
Operator imports still require Basic Auth, the exact Origin and `X-Jood-CSRF: 1`.

Use `/api/v1/import/registry` for identities and existing credential verifiers,
`/api/v1/import/observation?cluster=...` for the latest saved inventory and its
original receipt times, and `/api/v1/import/history?cluster=...` for bounded
historical points and lifecycle records. The archive import route
`/api/v1/import/archive?cluster=...` restores a complete immutable partition
without passing through the live queue. Raw restores regenerate modern
five-minute and hourly summaries. Existing archives with different content
return a conflict. Retries of an identical completed restore are idempotent.

`/api/v1/import/archives?cluster=...` accepts up to 32 complete partitions within
the same bounded request size. It keeps one cluster writer while uploading
independent immutable objects in bounded groups, then commits five-minute
summaries before rebuilding affected hours. A failed batch may have durably
stored some objects; retry the same inputs and require all receipts before
marking the batch complete or opening live ingestion.

After a base restore, `/api/v1/import/reconcile-archives?cluster=...` applies
bounded complete replacements and deletion records. Replacements require the
expected current content hash, or `null` for a previously absent partition.
Deletion records require the current hash and the complete scoped archive
identity. Stale preconditions return `409`; identical completed retries are
idempotent. A partial archive batch can persist some operations, so require all
receipts and final read-back verification. Superseded objects keep their garbage
collection grace period. Fresh raw replacements rebuild affected summaries;
expired raw deletions preserve already committed historical summaries.

`/api/v1/import/reconcile-events?cluster=...` applies checked event updates and
tombstones in one Durable Object transaction. `/api/v1/import/reconcile-state`
sets the source's saved inventory, heartbeat, profile, receipt times and latest
metric observations, with an expected state hash. It preserves source clocks
rather than marking an imported observation fresh. Apply state only after its
history and registry have been reconciled.

For a final incremental reconciliation, capture source row membership and
changes to existing rows, including source retention deletions. A maximum ID or
timestamp alone misses same-ID updates, late arrivals and deleted rows. Fence
every source writer, including background maintenance, and prove the final
boundary before enabling the target. Any source change journal must be installed
and validated under the source owner's resource and failure controls.

For legacy inventory observations that never recorded a profile, heartbeat or
receipt time, preserve those fields as `null`. Historical snapshots report
`observationMetadataAvailable` rather than borrowing current acknowledgments.

Bulk migrations may store an immutable `inventory-content` object once and
reference it from daily `inventory-receipts` archives. Receipt IDs and original
source nanoseconds determine historical ordering. Content must exist, pass its
checksum and remain retained at least as long as every referencing receipt.

Legacy summary, change and pending-rollup records can be preserved as
`legacy-rollups`, `legacy-changes` and `legacy-dirty` archives. These are retained
source evidence; they are not presented as modern summaries with fields absent
from the source. Record original row counts, time bounds and conversion digests
in a protected migration receipt.

Authenticated `/api/v1/export/archives?workspace=...&cluster=...` lists archive
indexes with a cursor. `/api/v1/export/archive?workspace=...&cluster=...&id=...`
reads and checksum-verifies an indexed object. Keep exports private. Enumeration
while a writer is active is not a consistent backup: fence writes, drain pending
work and verify the same boundary before creating a recovery manifest. Recovery
also needs registry verifiers and Durable Object state; telemetry exports alone
do not recover enrollment or acknowledgments.

`/api/v1/import/drain?cluster=...` drains bounded pending archival work while
machine ingestion is fenced, including the current partial source bucket.
Repeat until buffered points, dirty partitions and pending inventories are zero.
Protected `/api/v1/export/state` then exports saved observation metadata, exact
latest points and their state hash. `/api/v1/export/events` enumerates lifecycle
records in pages with checksums. Both exports require workspace and cluster scope.
These are parts of a recovery manifest; registry verifiers, referenced R2 objects
and any retry state still require coordinated protected backup.

Record the cluster status's `metricSequence` and `revision` at the writer boundary.
Archive enumeration accepts `receivedSince` to select indexes saved after that
boundary, independently of their source-time interval. Its boundary millisecond
is included conservatively. Fence and drain before a reverse export, then use
the recorded sequence and original identities to select post-boundary samples;
a source-time filter alone would omit late arrivals. Read back the selected
objects and reconcile observation, registry and event changes separately before
returning writes to an earlier hub. Export selection is not a completed rollback
or a substitute for a tested target-to-source replay adapter.

After parity and recovery checks, redeploy without `MONITOR_MIGRATION`. Confirm
import routes return `403` and only then redirect live agents to the target.

For a coordinated initial acceptance window, `MONITOR_RECOVERY=1` keeps normal
telemetry ingestion open while freezing operator mutations and new enrollment.
It suspends expiration and records batch identity, accepted semantic point keys,
rejected count, receipt time, sequence and revision in the same SQLite transaction
before acknowledgment. A recovery receipt identifies the durable raw records;
it does not contain Authorization headers, credential verifiers or wire payloads.
The journal has a separate 64 MiB logical limit and also counts toward the normal
buffer quota. Exhaustion rolls back the entire acceptance and returns retryable
backpressure. Monitor `recoveryJournalBytes` and conclude the acceptance window
before its measured capacity is exhausted.

Protected `/api/v1/export/batches?workspace=...&cluster=...` returns checksummed
receipts in pages of ten, with an optional inclusive `receivedSince` boundary
and opaque cursor. Following a writer fence and drain, reconstruct every receipt's
point keys from verified raw archives, including retries of records already
present at the boundary. Sequence numbers alone do not identify all retry
memberships. Reconcile current observation and lifecycle state as well. This
window still requires a rehearsed reverse adapter and independently verified
recovery; it does not perform rollback automatically.

Remove `MONITOR_RECOVERY` after acceptance and the protected recovery manifest
are retained. Normal expiration resumes; receipts expire after one day and
ordinary batch deduplication retains its existing seven-day horizon. Unconfigured
deployments do not record the temporary recovery journal.

## Upgrades

Review release notes and immutable artifacts. Validate new Prisma contracts and
migrations locally, then run native workerd recovery tests and staging checks.
Go agent images are built manually; deploy a reviewed digest. Keep existing
credentials and infrastructure ownership intact.
